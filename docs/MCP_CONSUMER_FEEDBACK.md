## 2026-10-18：担当エージェントへの依頼 — AIと人間が同じデザインを編集する

### 目的と今回の実例

既存の完成画像をそのまま流用する経路に加え、AIがWHATIFのレイヤー付きエディタを使って、新しいアートワークを作れるようにしたい。まずEP0402「まだ温かい」MVのYouTubeサムネイルを実例にする。制作済みの夕焼け背景・電車内装・切り抜き人物を、YouTubeプリセットの横長キャンバスに別レイヤーで配置し、文字を加える。人間が同じデザインを開いて位置・文字・構図を調整できることが目的。

制作プロジェクト：`/Users/kaya.matsumoto/projects/gen-video/projects/whatif/2026-10-17_mada-atatakai-mv`。採用素材と完成映像は同ディレクトリのREADME、`release/RELEASE.md`、`release/asset-sources.json`、最新AEプロジェクトから確認する。最初に素材の実体と透過・寸法を確認し、旧版やギャラリー原画を今回の切り抜き素材と混同しない。YouTubeプリセットの実際の定義を確認し、今回の想定は1920×1080。

### すでに確認できたこと／未調査のこと

- 例示デザイン：<https://whatif-ep.xyz/edit/03660d48-7656-432e-be67-f29497bad3d9>（EPISODE #400 (Copy)）。これは仕組みの検証用であり、今回のEP0402素材ではない。既存デザインを上書きしない。
- 公開GET `/api/ref/designs/03660d48-7656-432e-be67-f29497bad3d9/layers` で1920×1080、画像9レイヤー、元画像URL・配置・サイズ・重なり順・回転・不透明度を取得できた。元画像実体はRGB背景1枚、透過を含むRGBA画像8枚。テキスト層はない。このデザインの完成画像URLも取得できた。
- 読み取り経路は実在する。AI向けの作成・更新・素材登録・書き出し経路と、その認証・権限はまだ調査していない。機能不足と決めつけず、既存の保存処理・API・MCPを調べて再利用してほしい。

### 希望する制作フロー

1. AIが認証された本人の権限で、既存素材を参照、必要ならローカルの制作素材を登録する。
2. YouTubeプリセットで新規の下書きを作り、画像と編集可能なテキストを配置する。デザインID、レイヤーID、編集URLを取得する。
3. サイトの既存描画処理でプレビューを生成する。AIが画像を見て確認し、同じ下書きを修正する。
4. 人間が編集URLを自分のログイン済みブラウザで開き、通常のエディタで微調整・保存する。
5. AIが最新版を再取得でき、必要なら追加修正する。人間の変更後に古い状態を丸ごと書き戻さない。
6. 最新revisionの完成画像を生成し、画像URL・実寸・生成状態を取得する。同じレイヤー構造をRemotion等でも参照できる。

推奨案は「作成・更新は認証済みAPI/MCP、見た目は既存エディタと同じ描画処理、人間は編集URL」。ヘッドレスブラウザは既存描画エンジンの実行手段として必要なら使う。別レンダラの新設や独自JSON仕様の並立は必須ではない。ブラウザUI操作も当面の手段として認め、本人プロファイルでの共同作業とバックエンド操作のどちらを採るかは、現状の実装を調査して判断してほしい。

### 最小限の要件と受け入れ条件

- プリセット一覧と寸法、既存素材の検索・登録、レイヤー付き下書きの作成・読み取り・更新を、AIが扱える経路で利用できる。
- 操作は本人所有の下書きに限定した認証・認可を通す。公開Refの読み取り経路をそのまま匿名書き込みに拡張しない。所有者・認証トークンをAIの任意入力で偽装させない。
- 保存は既存のドキュメント形式・検証・revision処理を再利用する。再試行で下書きが重複せず、古いrevisionの更新は競合として検出する。競合時は再取得して人間の変更を維持する。
- 元画像・テキスト・配置が編集画面で保持される。フォント、クロップ、効果など外部再現に制限があれば明示する。見た目の検証は実画像で行う。
- 同revisionのプレビュー／完成画像の状態とURL・実寸を返す。未生成・失敗・古い画像をreadyと誤認しない。詳細は下の「公開作品の完成画像」節と併せて扱う。
- EP0402素材から新規下書き1件を作り、編集URLを人間が開ける。人間の変更を読み戻し、最新版から1920×1080画像を取得できることを確認する。Remotionとの新規連携実装は今回の必須範囲にしないが、既存レイヤー取得を壊さない。

### 担当エージェントに回答・対応してほしいこと

まず既存機能でできる範囲と不足を調査し、推奨経路、最小変更、検証方法を回答してほしい。可能なら既存の保存・描画処理を活かして不足機能を実装し、上記の小さな一連の操作で検証する。API名・ジョブ基盤・状態名などは提案であり実装を固定しない。一般的なデザイン自動化基盤の大改修より、今回の下書き作成と人間による編集を優先する。

ユーザーは調査と必要な改善を依頼している。ただし本番公開・有料処理・破壊的変更まで一括で許可されたとは扱わず、適用範囲はプロジェクトのAGENTSに従う。特にSupabase書き込みは所定のプロジェクト確認と個別の明示許可が必要。コード変更、検証済み／未検証、移行・デプロイの残作業、実際に利用する手順を分けて報告する。APIの確定仕様は [REF_LIBRARY.md](./REF_LIBRARY.md)、描画・revision設計は既存ADR等の正本へ反映し、この依頼書を別仕様の正本にしない。

## 2026-10-18：公開作品の完成画像を取得できる状態にする

EP0402のMV公開準備で、横長・縦長の完成画像をMCPから探した。保存デザイン3件は `previewStatus: ready` / `stale: false` だが `url: null`。一方、同作品の公開壁紙ページには取得可能な `pc-hd.png`（実寸1920×1080）と `mobile-hd.png`（1080×1920）があった。利用者には「まだ一度もダウンロードされていないから生成されていないのか」と見えた。

### 現行の仕組みについて確認したこと

- 保存デザインのfull-resは、エディタの保存・退出時にプレビュー生成が走る経路で作られる。壁紙の初回ダウンロードが生成条件ではない。実装は `src/components/editor/pages/BannerEditor.tsx`、仕様は [REF_LIBRARY.md](./REF_LIBRARY.md) の「画質と full-res の生成条件」。今回の欠損の発生原因自体は未特定。
- テンプレートの壁紙書き出しは、クライアントで描画してダウンロードする経路もある。`src/components/editor/components/TemplateWallpaperExporter.tsx` の処理だけでは、永続的な参照URLの登録は保証されない。
- MCPのdesign `url` は、そのデザインのfull-resを返す。公開壁紙のproduction画像が別にあっても自動では結び付かない（`src/lib/ref/designs.ts`）。今回の公開HD壁紙はすでに存在し、保存デザインの `url: null` は「作品の完成画像がどこにもない」という意味ではなかった。
- ページのQHD表記と、参照したHDファイルの実寸は別。利用者には取得ファイルそのものの寸法が必要。

### 管理者への提案（未実装・採否未決定）

1. **公開ラインナップに載せる時点で、配布・参照に必要な完成画像の存在と鮮度を確認する。** 未生成・旧revisionなら対象作品の必要な形式だけ生成し、完了後に「素材取得可能」とする。ダウンロードを待たず、一度作った同revisionの出力は再利用する。既存の保存・公開処理への組み込みから検討し、新しいサーバーレンダラを前提にしない。
2. **プレビューのreadyと、完成画像のreadyを区別する。** 完成画像について `missing / queued / rendering / ready / stale / failed` などの状態、実寸、生成revision、生成日時を示す。URLが空なら「エディタを開いて保存」等の次の操作も返す。既存 `previewStatus` の意味は黙って変更しない。
3. **作品IDを入口に、利用可能な出力を一覧化する。** 例：EP0402 → 横長HD／縦長HD／Feed、各URL・実寸・状態・元デザインへのリンク。design、asset、公開壁紙を区別したまま関連付け、利用者が別ページを手探りしなくて済むようにする。
4. **管理画面に対象を絞った「未生成分を生成」「失敗分を再試行」を置く。** revisionと形式をキーに重複生成を防ぐ。サムネイルを完成画像として代用しない。公開壁紙の再利用も、作品・構図・revision・解像度・公開権限が一致するときだけ行い、有料配布ファイルの権限を迂回しない。

過去の「全デザインを一括再レンダーする必要はない」という2026-09-04の判断は維持する。本提案は、その判断を実装指示で覆すものではなく、**公開対象の作品について、ラインナップと利用可能な完成画像を揃えたい**という今回の追加要望。API詳細仕様の正本は引き続き [REF_LIBRARY.md](./REF_LIBRARY.md)。

EP0402の取得結果・候補URLは、制作側の `2026-10-17_mada-atatakai-mv/release/asset-sources.json` に記録済み。今回の調査では生成・再保存・公開設定の変更は行っていない。

## ⚠️ `role: "character_cutout"` が透過を保証しない

前回「`character_cutout` は透過PNGだった」と報告しましたが、**全件そうではありませんでした。**

```
character_cutout 81件の内訳: PNG 69件 / JPEG 12件
```

**JPEG はアルファチャンネルを持てない**ので、この12件は透過なしです。

### 実例

`work=301` の唯一の素材 `0301_raw_x4_re.jpg`（3000×1912 / JPEG / mode=RGB）は、
中身を見たところ**切り抜きではなく元絵そのまま**でした。
`EPISODE 0301-1 Landscape` と同じ構図の、より広いクロップです。
名前の `raw` もそれを示しています。

### 何が困るか

利用側が **`role` を見て「透過が使える」と判断できません。**
`role: "character_cutout"` で引いた12件は、重ねると背景が四角く残ります。
いまは1件ずつ実体をダウンロードして確認するしかない状態です。

さらに、この素材に引きずられて実害が出ます。
`EPISODE 0301-1` を**レイヤー分けしてアニメーションさせようとすると、
「キャラの切り抜きがある」と見えるのに実際には無い**、という判断ミスが起きます。

### 提案（どちらでも）

- **`hasAlpha: boolean`（または `format: "png" | "jpg"`）をレコードに足す**
  → 利用側が取得前に弾ける。**これが一番安いと思います**
- `role` の意味を「透過切り抜き」に厳格化し、`raw` な元絵は別ロール（`source` など）に移す

前回書いた「`role: "background"` が欲しい」と根は同じ話で、
**ロールが実体を保証してくれると、取ってから確認する往復が消えます。**

## 参考：デザイン側は形式も置き場所もバラバラでした

問題ではないのですが、利用側の実装で気づいた点として。

| デザイン | `url` の形式 | パス |
|---|---|---|
| `IMAGINE #001` | JPEG 256KB | `/banners/{id}/full/…` |
| `EPISODE 0301-1 Landscape` | **PNG 4.8MB**（RGBA・ただしアルファは全面不透明） | **`/downloads/…`** |

URLをそのまま渡す使い方では困りませんが、
**サイズが20倍違う**ので、base64で埋める経路だと効いてきます
（4.8MB → base64で約6.4MB）。
`fileSize` が `fields` で取れると、事前に見積もれて助かります。
